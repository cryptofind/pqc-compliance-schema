## Repeatable cdxgen benchmark

`tools/run_cdxgen_benchmark.py` runs cdxgen against the nine treatment targets H1-H9
(H0 is the direct-use baseline and is not included in this nine-case run). It uses
`cdxgen --include-crypto -o <output-file> <target>` for each case and writes each
run to a new UTC-timestamped directory under `results/cdxgen/`; existing runs are
never overwritten.

Create the manifest from the ground-truth JSON once, then run the benchmark:

```bash
python tools/run_cdxgen_benchmark.py --write-manifest
python tools/run_cdxgen_benchmark.py
```

The checked-in `cdxgen_manifest.json` is the case-by-case expected-algorithm source
for scoring. The script refuses to overwrite an existing manifest or run directory.
Expected names come from resolved assets in the ground truth, never from cdxgen
findings. Each run contains a manifest snapshot, cdxgen version,
individual BOMs, logs, result records, `summary.json`, and `report.md`.

Scoring uses exact normalized algorithm-name matching (case-folded and
non-alphanumeric characters removed), and considers only CycloneDX components
whose type is `cryptographic-asset`. Ordinary dependency components do not count.
Resolved active, unreachable, and dead-branch assets are expected; conditional
assets are included because the benchmark scans source. Registry-only assets and
unresolved identities are retained in the manifest as exclusions, not included
in the primary TP/FP/missed score. A successful scan (zero exit and parseable BOM)
is reported separately from detection success. The harness does not run the
applications, and scan logs should be reviewed for tool warnings and limitations.

## Hypotheses and what to measure

| H | Target | What is manipulated | Primary measurement |
|---|---|---|---|
| H1 | `h01_metaprogramming` | Identity injected by an AST-rewriting macro decorator (AES-256-GCM, ML-KEM-768), `exec` of a generated template (HKDF-SHA-384), a metaclass (ECDSA P-384), dynamic import from string fragments (X25519), and a base64 payload (ChaCha20-Poly1305) | Detection level per technique, and whether the evidence points at the template/declaration or at the invocation |
| H2 | `h02_abstraction` | Import alias, re-export, factory/registry dispatch, closure pipeline, `functools.partial`, dispatch table, context manager, `cached_property` | Detection and parameter recovery per indirection |
| H3 | `h03_dependencies` | PyNaCl (compiled libsodium), PyJWT default HS256 and explicit ES384, itsdangerous and pyotp HMAC-SHA1 defaults, Fernet, vendored `third_party/sealkit` | Whether implicit defaults and compiled code surface; whether vendored code is scanned and attributed to the dependency |
| H4 | `h04_mixed_classical_pqc` | Seven units: hybrid key exchange, composite signature, post-quantum key exchange with ECDSA authentication, RSA envelope, downgrade fallback, all-PQC control, CNSA-grade hybrid | Per-unit verdict versus ground truth under each policy (table below) |
| H5 | `h05_misleading_names` | Identical code under misleading versus neutral names, the inverse case (post-quantum names on X25519 and RSA code), and decoy labels | Misleading-minus-neutral difference per pair; false RSA/ECDSA findings; false post-quantum findings |
| H6 | `h06_external_config` | Nine selections, each from a different source; registry entries that are never selected | Detection, parameter recovery, configuration-file evidence, over-approximation |
| H7 | `h07_call_depth` | Tracks A and E: crypto local to the deepest function. B: key size propagated within a module. C: across modules. D: through object fields | Deepest depth reached at L1 (family) and at L2 (key size) per track |
| H8 | `h08_policy_probe` | 23 units whose verdict vectors differ between every pair of reference policies | Default-policy fingerprint, configured verdicts, and how each tool's mechanism works (table below) |
| H9 | `h09_confidence` | Ten items with ideal confidence 5 down to 1, plus five decoys | Whether confidence values exist; rank correlation with the ideal order; decoy false positives |
